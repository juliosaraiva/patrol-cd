# patrol-cd

Patrol CD, a Kubernetes-native continuous delivery platform: API server and web UI, application controller, repo-server, ApplicationSet and notifications controllers, commit-server (source hydrator) and optional Dex.

| Chart version | App version | Kubernetes |
|---------------|-------------|------------|
| 0.1.0 | 0.1.0 | `>=1.30.0-0` (the Argo CD v3.5.5 baseline is tested on 1.33–1.36) |

This file is generated by `go run ./hack/helmdocs` from `README.md.gotmpl` and the `# --`
comments of `values.yaml`. Do not edit it by hand. The installation guide is
[`docs/guides/installation.md`](../../../docs/guides/installation.md).

## Install

```bash
helm upgrade --install patrol deploy/helm/patrol-cd \
  --namespace patrol --create-namespace --wait
patrol admin initial-password -n patrol   # the generated admin password
```

The chart is not published to a registry yet; install it from a checkout or from the archive
built by `make helm-package` (`dist/patrol-cd-0.1.0.tgz`).

## What gets installed

| Component | Workload | Default | Notes |
|-----------|----------|---------|-------|
| patrol-server | Deployment `<prefix>-server` | on | API, web UI, webhooks; runs the `bootstrap` init container |
| application controller | StatefulSet `<prefix>-controller` | on | sharded by shard Leases; headless Service `<prefix>-controller` (tree API, port 8090) |
| repo-server | Deployment `<prefix>-repo-server` | on | no Kubernetes token; optional CMP sidecars |
| ApplicationSet controller | Deployment `<prefix>-applicationset-controller` | on | leader-elected |
| notifications controller | Deployment `<prefix>-notifications-controller` | on | leader-elected |
| commit-server | Deployment `<prefix>-commit-server` | with `hydrator.enabled` | no Kubernetes token |
| Dex | Deployment `<prefix>-dex-server` | off | upstream image pinned by digest |
| CRDs and Operation admission policy | cluster-scoped | on | kept on uninstall |

`<prefix>` is `patrol` unless `fullnameOverride` is set (at most 40 characters). Workload,
Service and ServiceAccount names are cut to 63 characters; the metrics Services cut the base
before adding `-metrics`. With `<component>.serviceAccount.create: false`,
`<component>.serviceAccount.name` is required: the chart binds the component's RBAC to that
ServiceAccount and never to the namespace's `default` one. The settings objects keep fixed,
namespaced names: `patrol-cm`, `patrol-rbac-cm`, `patrol-cmd-params-cm`,
`patrol-tls-certs-cm`, `patrol-ssh-known-hosts-cm`, `patrol-gpg-keys-cm`,
`patrol-notifications-cm`, `patrol-secret`, `patrol-notifications-secret`,
`patrol-internal-token`, `patrol-initial-admin-secret`. Install one release per namespace.
Cluster-scoped objects are named `<namespace>-<prefix>-<component>`.

## First run and secrets

No template renders a random value and the chart never calls `lookup`: `helm template`
output is deterministic and identical in structure to the static manifests. The
`patrolcd bootstrap` init container of the primary workload (patrol-server, or the controller
when the server is disabled) creates, only when absent:

- `patrol-internal-token` (key `token`): the shared token of the internal APIs;
- `patrol-secret` keys `server.secretkey`, `admin.password`, `admin.passwordMtime`;
- `patrol-initial-admin-secret` (key `password`);
- `patrol-ssh-known-hosts-cm` key `ssh_known_hosts`: the published host keys of GitHub,
  Bitbucket Cloud, GitLab.com and Azure DevOps, unless `configs.sshKnownHosts` is set. The chart
  renders that ConfigMap without the key, so the known hosts managed through the API
  (`patrol cert add-ssh`/`rm`, UI) are never owned by Helm and survive upgrades.

It runs with the primary workload's ServiceAccount, to which the chart binds a narrow Role
(`create` on Secrets; `get` on those three Secrets, `update` on `patrol-secret` and `delete` on
`patrol-initial-admin-secret` (a stale one, older than `patrol-secret`, is replaced), by name;
`get` on `patrol-cm`; `get` and `update` on `patrol-ssh-known-hosts-cm` when it seeds it).
Supply your own material with `configs.internalToken.existingSecret` and
`configs.secret.adminPasswordHash`. `configs.secret.createAdmin: false` only skips the generated
password: the admin account stays enabled without a password unless `configs.cm."admin.enabled"`
is `"false"` (set both for SSO-only installations). Other workloads wait for the internal token
Secret before they start (their volume mount retries until it exists).

## Profiles

`ci/*.yaml` are tested value sets (`make helm-lint`, `make helm-template`):

| File | Purpose |
|------|---------|
| `minimal.yaml` | single replica, no NetworkPolicies, no PDBs, plaintext internal APIs |
| `default.yaml` | the chart defaults |
| `hardened.yaml` | strict egress, internal TLS with existing Secrets, no in-cluster write access for the server, controller writes limited to listed kinds (not a containment boundary: see the installation guide) |

| `core.yaml` | headless: controller, repo-server, ApplicationSet and notifications controllers |
| `hydrator.yaml` | source hydrator with the commit-server |
| `airgap.yaml` | mirror registry for every image, digest pinning |
| `namespaced.yaml` | namespace-install semantics (Roles only, no CRDs) |
| `ingress-nginx.yaml` | ingress-nginx with TLS termination at the controller |
| `all-features.yaml` | every optional template path (coverage, not a recommendation) |
