## Where each result comes from

The **Source** column of the step table says how a result was obtained:

- **script** — a committed, re-runnable script produced it and fails when it does not hold (the
  script and, where it has several, the check are named). Its output was kept as a session log.
- **by hand** — commands typed during the session, whose output was read but not kept as a log.
  Nothing re-runs these; they are observations, not tests. Numbers marked "(by hand)" have no
  log behind them.

The session logs were written to the session scratchpad and are not committed. Verbatim
excerpts of every log cited here, plus the read-only cluster observations made for this record

| KV-1 | defect (high) | The repo-server crashed on start on any volume mount root: `reposerver: root dir permissions: chmod /var/lib/patrol/repo: operation not permitted`. Hardened after the second review (GO-1): the fallback applies only when the root dir is owned by root or by the process, and `_patrol-repo` must be a real directory owned by the process (a symlink, a file or a foreign directory is refused). ## Not covered

- One CNI (kindnet) and one architecture (arm64); `linux/amd64` was not built or run. Other CNIs
  differ in whether `ipBlock` matches pod IPs and in how the API server is addressed.
- One replica of each component: no HA, no controller sharding across replicas, no leader
  election failover. The `ha` variants were not installed.
- Not exercised: SSO and Dex, ingress, webhooks, ApplicationSets and their generators, the
  source hydrator and commit-server, CMP plugins, notifications delivery, the web UI beyond its
  first response (no browser run, no Playwright), GitHub integration (no live GitHub), sync
  waves and hooks, prune, rollback of an Application, multi-cluster beyond one destination,
  upgrade from an earlier version, backup and restore, performance and load.
- Not exercised against a kubelet: pod logs and the web terminal (neither through the API nor
  the CLI); live resources and resource actions of the destination cluster. Port-forward was
  used only by hand, by CLI core mode, to reach the control cluster's repo-server and
  controller (step 15).
- The namespace-scoped manifests and the `core-install` / hydrator variants were not applied to a
  cluster; only `cluster-install` was, by hand.
- No committed check covers: the static manifests on a cluster, CLI core mode on kind, metric
  contents, seccomp, the absence of the repo-server's service account token, the deletion of a
  managed Service, or the internal token surviving an uninstall (steps 9 to 15, by hand).
- No vulnerability or license scan, no SBOM.
